現有系統架構的四個關鍵問題

整份系統目前是「每個 module 自己讀寫 localStorage」的架構，沒有中央資料庫、沒有共用 service layer。 NEC Option 只是 Project 上的一個欄位，並沒有成為資料分區（namespace）。以下逐項交代資料存放方式、 每個 Option 在每個 Module 顯示什麼、Table 格式是否真的跟 Option 對齊，以及 Module 之間是否偷偷互相取數。

專案：ai-progress-checking / studio 儲存層：localStorage（無 DB / 無 API） 模組：5 個主模組 + 3 個內嵌工作區 選項：NEC A–F 日期：26 Nov 2026

五個最重要的判斷

1. 資料隔離只有一個維度：projectId。 Option 存在 apc.projects.v1 的 necOption 欄位，但所有資料 key 都只是 <base>:<projectId>。同一 project 內無法同時保留 Option A 與 Option C 的資料； 要比較兩個 Option 只能開兩個 project。
2. 沒有中央資料庫，Modules 直接讀 localStorage。 12 個專案級 key 由 9 個檔案各自讀寫，沒有 repository / store / context 統一入口； 其中 4 處是「A 模組直接解析 B 模組的 private key」。
3. Option 只影響「顯示哪些 tab」，不影響「資料結構」。 真正 branch 的只有 FlowTabs（A/C 顯示 AS）、DocumentManagement、CompensationEventPage（CE 連結目標）、 BimMapping（主文件是 AS 還是 BQ）。Table 欄位完全沒有按 Option 改變。
4. Table 格式是由「Flow（BQ / AS）」與「Pricing mode」決定，不是由 Option 決定。 A 與 B 用的是同一張 BqTable；Option E / F 的專屬欄位（cost records、target cost）不存在。
5. 模組可以獨立 build / 獨立開頁，但不可以獨立運作資料。 Measurement Library 是唯一真正獨立的模組；Mapping Model、Cost result、CE、Subletting 都依賴別人的資料或 demo 常數。

Option / Project 的實際隔離行為

問題現況判斷
Option 是不是資料分區？ 不是。Option 只是 project 物件的屬性，不會出現在任何 storage key。 No
同一 project 可否同時有 Option A 與 C 的資料？ 不可以。要並存只能建兩個 project，但兩個 project 又各自用自己的 key。 No
切換 project 時資料會否混在一起？ 不會（key 有 projectId）。但 3 個模組的元件用 key={projectId} 強制 remount， 而 Mapping Model 的存檔 effect 只依賴 [scenarios]，切 project 後有機會寫回舊 key。 Partial
Option 可否中途改？ Project Home 建立時選定；資料結構不隨 Option 改變，所以改了 Option 不會壞資料，但已存在的表格欄位也不會跟著變。 Mutable
有沒有版本 / migration？ 只有 key 名稱裡的 .v1 / .v2 / .v3，讀取時寬鬆驗證，舊版本資料不會自動升級。 Key-only
多分頁 / 多使用者？ 每個 tab 各自持有 state，寫入是 last-write-wins；沒有鎖、沒有衝突處理。 None
容量風險：CE 原檔縮圖與 IFC 資產都存在 localStorage（一般 5–10 MB）。 apc.ce-records.v2 把 base64 JPEG 一併寫入，檔案多幾份就會 QuotaExceededError，而目前所有寫入都是靜默失敗。

主文件標籤跟 Option

三個具體的錯位

1. Option E / F 仍在用「BQ 為主」的表格。 E 是 cost reimbursable，理論上主表應該是 invoice / actual cost；F 是 management contract，主表應該是 AS + cost。 但兩者現在都只看到 BQ 表，而且 FlowTabs 的排序邏輯寫死為 activityMain ? [AS,BQ,CE] : [BQ,CE]。
2. Option C / D 沒有任何 target cost 欄位。 Target cost 的 pain/gain、target price、defined cost 在表格中完全缺席； C 與 A 的畫面逐格相同，D 與 B 亦相同。
3. AS 表帶着 BQ 的欄位。 AS 表同樣有 Qty (BIM)、Amount (BIM)、Final Amount， 這些是 BQ / 量差比較的概念；Activity Schedule 真正需要的是 schedule 分組、完成百分比、CE 對應，目前只有 schedule 分段。

建議的目標架構（方向，不是實作）

三層切開： ① Option 能力表（單一 NEC_OPTION_INFO：主文件、必需文件、可用 module、table schema）→ ② Data repository（每個 domain 一個 module，統一 key、版本、join）→ ③ View（只收 props，不碰 localStorage）。 這樣 Option 就由「一個顯示開關」變成「驅動資料與欄位的設定」，而 module 之間的耦合只會出現在 repository 層。
